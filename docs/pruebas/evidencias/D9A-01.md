# D9A-01: cuenta desactivada con sesión accede a dashboard

Severidad: media / P2. Descubierto el 25/10/2026 en la evaluación del requisito 4. Estado: corregido y verificado mediante reproducción y regresiones. La gravedad corresponde a que una cuenta desactivada podía seguir consultando el dashboard con una sesión anterior; no se demostró acceso indebido a pedidos ni escalamiento de permisos.

## Reproducción conservada

La evidencia utiliza SQLite :memory:, verifica la conexión y crea exclusivamente una cuenta ficticia. Establece una sesión autenticada, desactiva esa cuenta y consulta dashboard. No usa la base real ni la copia de restauración.

```powershell
php -d auto_prepend_file=tests/bootstrap.php vendor/bin/phpunit tests/Feature/CuentaInactivaDiagnosticoTest.php
```

Resultado original antes de corregir: salida 1, un caso fallido, cinco aserciones. Esperado: redirección a login; recibido: HTTP 200. Mensaje: «Expected response status code [201, 301, 302, 303, 307, 308] but received 200».

Tras la autorización específica, el archivo se trasladó de evidencias a tests/Feature conservando su método y aserciones originales. Solo cambian namespace y descripción. Ahora se ejecuta una vez en la suite habitual, sin cambiar phpunit.xml. El fallo original queda documentado; no se elimina ni se disfraza como un resultado aprobado anterior.

## Causa e impacto comprobados

dashboard aplica auth. La comprobación de status existe en RoleMiddleware/PermisoMiddleware, pero no cubre todas las rutas autenticadas. La cuenta conserva acceso al dashboard hasta que una ruta con esos controles la expulse o cierre sesión. El control de permisos de pedidos sí redirige correctamente. No se afirma acceso indebido a pedidos ni movimientos de inventario.

## Corrección implementada

VerificarUsuarioActivo comprueba users.status, cuyo cast existente es booleano. Se incorpora al grupo web con prioridad después de iniciar la sesión y antes de la autenticación y los controles de cambio de contraseña, roles, permisos e idempotencia. Laravel obtiene el usuario de la sesión para cada nueva solicitud; no se conserva un estado activo entre solicitudes.

Si la cuenta está inactiva, reutiliza Auth::logout(), session()->invalidate() y regenerateToken(), como el cierre de sesión existente. Las solicitudes HTML redirigen a login con mensaje español; las que esperan JSON reciben 401 con mensaje español y sin Location. No hay rutas API ni autenticación por tokens configuradas: la protección corresponde a la autenticación web actual, incluidas sus solicitudes JSON. No se introduce un guard nuevo ni se modifican roles o permisos.

## Regresiones y resultado real

SesionUsuarioActivoTest verifica inicio de sesión real de los tres roles, permisos administrativos conservados, desactivación tras login, cambio de identificador y token CSRF, eliminación de datos y del identificador anterior en el almacenamiento de sesión, bloqueo posterior de pedidos, dos sesiones distintas previamente válidas expulsadas en su siguiente solicitud, JSON 401, cambio obligatorio de contraseña y login público sin bucle. Las 11 pruebas Security existentes conservan el rechazo de login inactivo y el cierre de sesión.

Ejecución focalizada después de la corrección: CuentaInactivaDiagnosticoTest y SesionUsuarioActivoTest, **9 aprobadas, 104 aserciones**, salida 0. El escenario de dos sesiones comprueba primero que ambas acceden activas al dashboard; no simula dos sesiones destruyendo una antes de desactivar la cuenta.
