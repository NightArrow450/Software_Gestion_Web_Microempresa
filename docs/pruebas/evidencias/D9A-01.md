# D9A-01: cuenta desactivada con sesión accede a dashboard

Severidad: media / P2. Estado: observado, corrección pendiente de autorización. Descubierto el 25/10/2026 en la evaluación del requisito 4. No se modificó código productivo.

## Reproducción conservada

La evidencia utiliza SQLite :memory:, verifica la conexión y crea exclusivamente una cuenta ficticia. Establece una sesión autenticada, desactiva esa cuenta y consulta dashboard. No usa la base real ni la copia de restauración.

```powershell
php -d auto_prepend_file=tests/bootstrap.php vendor/bin/phpunit docs/pruebas/evidencias/CuentaInactivaDiagnosticoTest.php
```

Resultado real: salida 1, un caso fallido, cinco aserciones. Esperado: redirección a login; recibido: HTTP 200. Mensaje: «Expected response status code [201, 301, 302, 303, 307, 308] but received 200».

El archivo se conserva fuera de las suites predeterminadas para ejecutar y revisar la reproducción explícitamente. No se modificó phpunit.xml, no se eliminó ninguna prueba ni se convirtió este resultado en aprobado. El informe y PR incluyen el fallo separado de las suites verdes.

## Causa e impacto comprobados

dashboard aplica auth. La comprobación de status existe en RoleMiddleware/PermisoMiddleware, pero no cubre todas las rutas autenticadas. La cuenta conserva acceso al dashboard hasta que una ruta con esos controles la expulse o cierre sesión. El control de permisos de pedidos sí redirige correctamente. No se afirma acceso indebido a pedidos ni movimientos de inventario.

## Corrección mínima propuesta, NO aplicada

Aplicar una comprobación de cuenta activa de manera uniforme a las rutas autenticadas, antes de permitir continuar. Si la cuenta está inactiva: logout, invalidar sesión, regenerar token y redirigir al login con mensaje español, reutilizando la semántica de los middleware existentes. No cambiar roles ni permisos.

Tras autorización: integrar esta regresión en tests/Feature, verificar dashboard/cambio de contraseña y rutas con permisos; preservar login público, salud, cierre de sesión y usuarios activos. Ejecutar las suites pertinentes y eliminar la duplicación del archivo diagnóstico solo mediante un traslado explícito, conservando el caso.

La propuesta requiere revisar también el orden del middleware; no debe alterar autenticación o idempotencia de operaciones. No se implementa silenciosamente dentro de pruebas finales.
